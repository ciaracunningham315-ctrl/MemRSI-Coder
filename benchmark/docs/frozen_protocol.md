## 1. 范围与文档效力

Benchmark 名称统一为 **EvoCode Benchmark**。固定范围为三个 Python 项目、每项目四个时序任务，共 12 个主任务；使用 A1/A2 与 B2/B3/B4 五组对照，报告五项核心指标及 NSRR。

“单项目四阶段端到端闭环”是完成整体 Benchmark 的实施步骤，使用相同的数据契约、状态规则和判分链路验证工程实现。它不会把正式题集缩减为四题，也不构成另一套 Benchmark。

本文件是执行依据；[`design_rationale.md`](design_rationale.md) 保留设计解释，遇到歧义以本文件为准。题目、隐藏测试、门禁规则、预算或模型配置发生影响可比性的变更时，记录变更原因、时间与哈希，建立新的实验批次并重跑受影响对照；不能混合变更前后的成绩。

r2 仅调整正式运行的并发调度、阶段屏障与轨迹归并规则；12 道主任务、54 个计划位置、门禁题、评分指标、模型配置和数据快照保持原契约。r1 与 r2 的运行记录不得合并；批次清单必须包含新的 `protocol_id` 和并发配置。

## 3. 研究问题与对照组

| 组别 | Raw-RAG | Task Skill | Evolution | Meta-Skill |
|---|---|---|---|---|
| A1 | OFF | OFF | OFF | 不消费 |
| A2 | ON | OFF | OFF | 不消费 |
| B2 | ON | 固定初始库 | OFF | 固定初始状态 |
| B3 | ON | 按阶段学习并经门禁发布 | ON | 固定 V1 |
| B4 | ON | 按阶段学习并经门禁发布 | ON | T2 后审查一次，允许发布候选新版本 |

比较 A2−A1 评估相同历史条件下的 Raw-RAG 增量；比较 B3−B2 评估 Task RSI 系统效果；比较 B4−B3 评估允许 Meta-Skill 进化的效果。

B 组会形成各自不同的运行历史，故组间差异属于持续学习系统整体效果。不能将 B3−B2 的全部差异归结为某一条 Skill 文本。

## 4. 题集与开发数据分离

现有 `tests/fixtures/prevalidation/` 保留为 Agent 开发与排错资料，不纳入正式主任务成绩。正式题集在 `benchmark/scenarios/` 独立制作，不复制已有留出题作为主测题。

| 项目 | 固定问题方向 | 四阶段要求 |
|---|---|---|
| repo_api | 输入校验、接口兼容与错误响应 | 同机制迁移，接口重构后验证旧经验，再测试组合边界 |
| repo_cli | 配置来源、覆盖顺序与参数边界 | 跨子命令迁移，配置加载接口变化，再测试多来源组合 |
| repo_data | 空值、类型转换、数值精度与字段变化 | 跨处理流程迁移，数据表示变化，再测试新数据组合 |

每条任务链定义：

- T1 Seed：产生真实任务轨迹与可复用经验。
- T2 Transfer：机制相关、具体实现不同，不能直接复制 T1 补丁。
- T3 Stale：代码或接口发生预设变化；同时保留有效与过期经验，检验适用性判断。
- T4 Held-out：与已学机制相关的新任务；不参与此前任何 Skill/Meta 提炼、选择或调参。

每题当前需求必须足以独立求解。所有组获得相同任务说明、代码、公开测试和环境；历史提供经验收益，不替代未向基线公开的验收需求。

题目准入要求：故障版本至少一项目标隐藏测试失败，参考修复全部通过；固定回归测试通过；检查代表性错误补丁不会仅凭删检查、吞异常或硬编码示例通过验收。所有准入记录保存真实命令、退出状态与日志。

### 4.1 T3 与现有适用性检查对齐

题目制作必须对齐 `MemoryService._applicability()` 实际可观察的证据：路径是否存在、历史文件 SHA256 是否变化、历史符号名称是否存在、依赖文件内容及 Git 祖先关系。当前 Python AST 检查只提取函数和类名称，**不比较参数签名**；只增加参数而保留名称，不能据此预期 `symbols: stale`。

`repo_api.T3` 的预设重构应改动 T1/T2 历史证据确实涉及的辅助函数或模块：在原模块中重命名旧函数，可检查 `symbols: stale`；迁移或删除旧模块，可检查 `paths: stale`；有历史内容证据的文件发生变化，可检查 `content: stale`。模块已经消失时，符号检查可能为 `unknown`，不能强制要求所有检查项同时为 `stale`。

准入检查需验证历史证据提取器能记录相应 `file_paths`、`symbols`、`content_evidence`，保存预期检查项、实际状态与原因；真实历史收集完成后再次核对提取结果，不以手写虚构轨迹替代。对照中保留一个未受影响的相关符号或模块，并覆盖仅有无关 Commit 变化的情况，避免全部旧经验都被标成过期。

T3 的成功依据仍是任务修复与独立验收。召回过期经验后识别失效条件并正确适配属于合理行为；仅发生召回、Commit 改变或整个文件哈希改变，均不能单独证明 Agent 具备了语义层面的适用性判断能力。

## 5. 快照与 Git 历史契约

每个阶段恢复预先制作的固定代码起点。Agent 在上一阶段产生的代码修改不直接传入下一阶段；可继承的对象只有协议允许的 Event Log、索引、Skill 和 Evolution 反馈。

同一项目各阶段使用稳定 `repository_id`，记录 `task_id`、`stage`、`code_snapshot_sha256`、`visible_head_sha`、`allowed_ancestor_shas`、阶段包哈希及私有验收文件哈希。清单属于 Runner 元数据，不整体注入模型。

阶段仓库包按时间逐步制作：T1 只能包含 T1 及其祖先对象，T2 才加入 T2 允许的历史，依此类推。完整仓库切换到旧 HEAD 不满足信息隔离要求。打包检查必须覆盖 refs、对象库、reflog、alternates、远程配置以及其他可读取的未来内容。

历史事件中的 Git 基线必须可以追溯。未提交修改另存补丁哈希与来源任务，不伪造已提交版本。`stale` 的判断依据相关文件、符号、接口或依赖实际变化；Commit 不同本身不等于失效，无法判定时记录 `unknown`。

## 6. 实验 A：公共冻结历史

公共历史由同一条真实 Agent 收集流程生成一次：Raw-RAG ON，Skill OFF，Evolution OFF，按 T1→T2→T3 阶段顺序执行；每阶段的三个仓库作为并发波次，全部任务终止后才合并历史并增量索引。检索只允许读取此前阶段。保留成功与失败轨迹，不按是否有利于 A2 筛选历史。

主测 T2 使用截至 T1 的历史，T3 使用截至 T2 的历史，T4 使用截至 T3 的历史。公共历史生成不使用主测隐藏测试、参考修复及其日志作为学习反馈。每个重复实验共用相同版本的公共历史，以测量固定历史条件下的执行波动。

A1/A2 对每道题克隆相同 SQLite、历史内容与已完成索引的快照。每个仓库的 A1/A2 是同步配对：两臂先各自启动隔离实例并完成健康检查，再同时派发；三个仓库配对可并发。向量集合名可不同，但事件映射与索引内容指纹必须一致。A1 在 Host Tool 层拒绝历史检索，清理跨会话摘要、缓存等旁路；保留当前任务的普通上下文与事件写入。每臂使用独立数据库、工作区和任务 ID，只共用只读冻结历史与索引。

每题都使用新会话和独立快照副本。当前主任务新写入的事件不得被其自身作为跨会话历史检索，主测结果也不回填公共 Seed。

收集流程与主任务执行期间均关闭后台索引；公共历史只在阶段边界增量索引并生成下一阶段快照。A1/A2 的任务副本不得自动补索引；显式索引操作也只能由 Runner 在协议允许的边界执行。检索入口排除当前 `task_id`，并校验允许的历史任务与事件边界；详细要求见第 7.1、9.1 节。

## 7. 实验 B：按阶段学习与继承

B2/B3/B4 从完全一致的初始 Event Log、Skill Registry 与 Meta-Skill V1 出发。初始状态单独制作、记录来源并冻结，不包含正式任务题目或答案，不额外加入未记录的外部进化反馈。

每个实验组从同一冻结初始状态独立克隆一份 SQLite 数据库；B2、B3、B4 之间数据库完全隔离。同组三个仓库共用该数据库与一个 Application/EventStore，以 `repository_id` 区分仓库轨迹、记忆和 Task Skill 作用域。阶段按以下屏障顺序执行；同一主任务波次中的三个仓库并发：

```text
并发 {repo_api.T1, repo_cli.T1, repo_data.T1}
  → 全部任务终止、固定顺序归并轨迹 → 增量索引与检索冻结
  → B3/B4 三仓库 Task Skill 提案并发 → 全部提案完成 → Gate 评估并发
  → 全部 Gate 终态 → 按 repo_api, repo_cli, repo_data 顺序发布
并发 {repo_api.T2, repo_cli.T2, repo_data.T2}
  → 同一阶段屏障与 Task Skill 批次
  → B4 等待三个 T2 Task 学习与门禁全部结束后执行 Meta Review
并发 {repo_api.T3, repo_cli.T3, repo_data.T3}
  → 同一阶段屏障与 Task Skill 批次 → 冻结 T4 快照
从同一组冻结快照独立克隆，并发 {repo_api.T4, repo_cli.T4, repo_data.T4}
```

同一阶段内，三个任务使用阶段开始时相同的 Skill 版本、历史截止边界和只读检索集合。每个 B 组内复用该组的 Application/EventStore，并为每个仓库创建唯一工作区和任务 ID；B2/B3/B4 使用互相独立的 SQLite 克隆。EventStore 使用 WAL；实例内以 `RLock` 和 `BEGIN IMMEDIATE` 排队写事务，跨连接冲突由 SQLite busy handler 等待最多 30 秒（`timeout=30.0`、`busy_timeout=30000`）。A 两臂及 T4 使用独立状态克隆。新事件可以即时持久化，但在下一阶段前不开放跨任务检索。所有主任务完成前不启动 grader；批次失败或预算耗尽时记录已完成项与缺测，不越过屏障、自动重跑生成请求或将不完整波次计为完整比较。

B3/B4 在 T1、T2、T3 批次结束后各执行一次阶段学习批次。三仓库 Task Skill 提案在同一活跃 Skill 快照下并发生成，所有提案完成后才启动 Gate 评估；所有评估进入终态后按固定仓库顺序发布通过的候选，避免早发布改变后发提案的输入。每批按仓库分别显式触发 Task Skill 提案，不能把三个仓库合并为一次未分作用域的 Project Skill 提案。实际提案、评估与发布数量另行记录，不把一次阶段学习批次误计为一次模型请求。

并发任务按实际 `task.created_at` 升序、同时间按协议仓库顺序、再按 `task_id` 排序归并。B4 Meta Review 的主任务轨迹与 Task 学习 run 列表按固定顺序显式传入，不依赖异步完成顺序或数据库默认排序。所有主任务按波次并发，判分在同波全部 Agent 终止后运行，降低 grader 与 Agent 争用资源造成的臂间差异。

Project Skill 只适用于其仓库；General Skill 可以在同一组内跨仓库复用，适用条件必须由提炼与门禁确认。候选经过独立发布门禁才能生效。B2 的 Skill 永远固定，但原始任务历史按相同阶段规则积累。

T4 开始前冻结各组历史、Task Skill、Meta-Skill 和索引；三个 T4 从该快照独立克隆。T4 不触发学习、不回写正式学习快照，禁止第一道 T4 的经验帮助后两道。

每个重复实验重新克隆初始状态。状态不得跨组、跨重复或从开发检查流入主测。

### 7.1 阶段边界与增量索引

Runner 启动主任务、公共历史收集及门禁分支时，固定设置 `raw_rag.background_indexing=false`；关闭后台循环不替代读取边界校验。阶段主任务读取阶段开始时的冻结索引，新事件只进入日志和待处理队列。

T1/T2/T3 阶段边界按以下顺序执行：

1. 等待该阶段全部任务进入已记录的终止状态，确认相关写入与作业结束，保存实际任务 ID 和允许进入后续历史的事件范围。
2. 由 Runner 显式处理符合范围的 pending 索引任务，复用 `MemoryService.index_pending()` 的增量能力，直至队列处理完成；核对失败数、残留任务、FTS/向量内容映射和服务健康。
3. 固化阶段结束时的 SQLite 检索内容与 Qdrant 集合，形成用于本次阶段学习门禁的同一份只读检索快照。门禁可使用刚结束阶段的允许历史；下一阶段主任务此前不能提前读取它。
4. B3/B4 执行第 7.2 节的阶段学习与门禁；T2 学习结束后额外执行 B4 Meta Review。B2 跳过学习，保持静态 Skill。
5. 学习、评估和发布作业完成后，冻结下一阶段的历史、索引描述和活跃 Skill 版本。门禁分支事件不导入主任务 Raw-RAG；学习过程产生的新增记录不能绕过已声明的历史边界。

当前 `POST /api/memory/rebuild` 对应的 `rebuild_index()` 会重置全部索引任务并重新向量化，**不得将它当作每阶段的增量索引接口**。实现时通过受控接口或 Runner 适配入口调用增量处理；全量 rebuild 仅用于明确记录的索引初始化或修复，开销单独记账，并重新验证快照指纹。

检索侧除按仓库过滤外，还必须排除当前 `task_id`，并限定允许的历史任务与事件范围。规则覆盖 FTS 候选、向量候选及回表、Episode 和邻近事件展开；不得只改 FTS SQL 后让向量或上下文展开旁路取回被排除内容。历史上界不能只使用各任务独立的 `seq` 作全局比较，应保存冻结快照标识及对应任务/事件范围。

T4 不执行阶段学习或主任务增量索引，其新增事件只作为独立结果产物保留。

### 7.2 显式学习接口与作业完成条件

实验 B 固定设置 `evolution.auto_trigger_enabled=false`，学习、评估、发布及 B4 Meta Review 均由 Runner 调度。`evolution.enabled` 按实验组设置，不能为了手动调度而把 B3/B4 的进化能力关闭。

`POST /api/evolution` 的实现需将 `trace_task_ids` 透传给 `EvolutionService.trigger()`。参数必须是非空、去重并按时间排序的实际任务 ID 列表；验证任务存在、已终止、属于本实验组和重复，且没有越过当前阶段。Task Skill 学习按预期仓库校验作用域，拒绝无效输入，不静默回退到默认最近任务抽样。

Task Skill 批次按仓库累计提供轨迹：T1 使用该仓库 T1；T2 使用 T1+T2；T3 使用 T1+T2+T3。允许生成 CREATE、REVISE 或其他受支持操作，但不强制候选产生、操作类型或晋升；记录实际输入与结果。

Runner 对每个候选依次执行 `trigger → evaluate → 查询并等待评估完成 → 通过后 publish`。当前 evaluate 接口返回“已调度”，不代表评估通过；只有实际评估完成且门禁通过才发布，无候选或失败时保留原因并结束该动作。

## 8. Meta-RSI 的生效与证据

B4 在三个 T2 均结束、T2 Task Skill 学习完成后，强制调度一次 Meta Review；B3 在相同位置记录边界并保持 V1。审查不足以晋升时保留 V1，记录真实原因。

正式运行显式传入三个仓库 T1+T2 的全部六个实际 `trace_task_ids`，不依赖 `batch_task_count` 的默认截取。单项目工程检查传入 repo_api 的 T1+T2 两个实际任务 ID，执行范围见第 11.1 节。任务轨迹选择不能替代 Evolution 反馈选择：同时限定反馈属于本组、本重复和 T2 审查边界，保存实际进入模型摘要的 `evolution_run_ids`、状态与截断情况，不能把列出的全部历史 ID 当作已完整进入模型的证明。

当前服务的 Meta 提案摘要存在数量上限；接口对齐后仍需核对模型输入与上下文预算。无法按协议提供所需轨迹或反馈时，记录输入不完整或预算不足，不静默丢弃后继续宣称完成全部材料审查。审查依赖 Task Skill 学习与评估反馈全部落盘；不以仅完成任务执行代替该屏障。

获准发布的 Meta-Skill 只指导此后的 Task Skill 学习，不直接作为 Coder 的 Task Skill 注入。主测观察链固定为：

```text
T1/T2 学习反馈 → T2 后 Meta Review → Meta 候选及门禁
→ T3 任务轨迹 → 新 Meta 指导 Task Skill 提炼 → Task Skill 门禁及发布
→ T4 实际加载 → 独立判分
```

T3 在线任务继续使用阶段开始时已有的 Task Skill。按照此规则，T4 是观察新 Meta 策略经后续学习产生效果的主要位置。Meta 发布门禁可在已允许的历史材料和独立 Gate 题上比较旧、新策略，但其临时派生 Task Skill 不直接导入主任务正式 Skill 库。

证据必须包含 Meta 父版本与内容哈希、提案和门禁记录、实际指导的学习批次、派生 Task Skill 版本及哈希、T4 路由与加载记录、与真实模型调用关联的上下文注入证据。只有文件生成或版本号变化不构成完整证据。

Meta 未晋升、后续 Skill 未晋升或未被使用时，分别报告实际状态；不得将 B4−B3 的成绩差直接表述为新 Meta 策略收益。

## 9. 发布门禁与外部判分

两者共用底层容器或命令执行能力，但使用独立数据与结果通路。

- Gate 使用 `private/gate_selection/` 的固定任务决定候选是否发布；可以向 Evolution 反馈受控门禁结果。
- Grader 使用 `private/acceptance/` 与 `private/regression/` 给主任务评分；题目内容、隐藏测试及日志不回传 Agent、Raw-RAG 或 Evolution。
- NSRR 独立评估使用 `private/gate_audit/`，不以 Gate 自己的结论充当外部标签。

Task Skill 发布沿用可执行对照原则：候选分支固定验收全部通过、旧版通过项无回归，且成功项增加，或在验收全部通过的可比集合中预先指定成本指标严格降低。预算、指标和具体实现哈希在运行批次前固化，不因某个候选未通过临时改变。Meta 门禁还必须验证旧、新策略派生 Skill 确实进入各自下游模型请求。

### 9.1 门禁分支的冻结混合检索

阶段门禁的 baseline/candidate 必须复用同一份冻结检索快照：SQLite 中的 `memory_chunks`/FTS、Qdrant point ID 与事件映射、Embedding/Reranker 配置及历史上界一致。该快照来自第 7.1 节的阶段结束屏障；不能将仍在写入的主实例集合直接称为冻结集合。

`Application.run_isolated()` 已提供关键字参数 `frozen_memory_collection`，但当前 `SandboxEvaluator._execute()` 调用 runner 时未透传。实现需由 Evaluator 或可信适配器将集合描述校验后，实际以关键字参数传给 `run_isolated()`；只在 snapshot 中增加同名字段，或只修改 snapshot 内的 `config.raw_rag.collection`，不能保证现有调用使用它。

每个评估分支保留独立可写 SQLite、工作区与 Skill 快照，Qdrant 使用调用方拥有的只读冻结集合；关闭后台及分支自动重建，禁止评估事件写回集合。同一门禁对照允许复用该组、该重复、该阶段的集合；组间与重复间不串用可变集合。实验 A 如复用公共只读 Seed 集合，必须保留相同内容指纹与各任务的独立运行状态。

Runner 保存集合存在性、索引完成度、内容指纹、模型标识和 SQLite 映射验证结果；保证所有消费者结束前集合不被清理或修改。当前向量搜索在集合 404 时可能返回空结果而外层仍标记 `mode=hybrid`，因此不能仅据该字段或一次零命中认定混合检索正常。合法零命中与集合缺失分别记录；验证失败时标注协议不符合，不静默以纯 FTS 门禁结果替代完整混合检索对照。

### 9.2 主任务独立判分

主任务判分流程：收集相对于固定起点的完整修改产物（含新增文件和必要删除），保存补丁与内容清单，在独立干净代码快照应用修改，然后注入可信隐藏测试并执行。禁止复用 Agent 工作目录内已被修改的测试、缓存或依赖环境作为判分权威。构建失败若由补丁引起，计为任务失败。

计分窗口以预算截止或正常结束为界。`solved` 由独立隐藏修复测试与回归测试全部通过决定，不由 Agent 自述或单一终态字段决定；预算内正常结束但未通过验收、Agent 超时或耗尽预算均计任务失败。基础设施故障记 `unverified`，保留计划分母、有效判分分母及覆盖率，不能静默删除。

## 10. 环境、预算与重复

正式主测执行一次，`repeat_id=1`、种子记录为 42。服务不支持随机种子时如实记录 `seed_supported=false`，不能宣称完全确定性复现。每次尝试只允许一次 Agent 执行，禁止挑选多次尝试中的最好成绩。Planner/Coder 固定使用 `qwen3.8-flash`，Agent 配置 Context 窗口保持 131,072 Token；Evolution 使用运行时实际配置，并在批次清单记录真实 `model_id`。本次协议/模型配置变化须建立新 `batch_id`，不能与旧批次结果合并。

所有主任务统一使用 600 秒在线执行上限和 80 次在线工具调用上限，服务 Context 硬上限为 131072 Token；具体模型输出上限、Agent 轮次上限及其他生成参数从批次清单固定并核对。开发检查可以用于发现预算不适配，变更必须发生在主测前并应用于所有可比组。

Planner/Coder 使用架构约定的同一服务；Evolution 使用架构约定的独立服务。运行前捕获真实 model_id、服务配置、模型参数、Prompt/代码指纹、容器镜像摘要、Python 与依赖锁、Embedding/Reranker 标识及索引内容指纹。不以文档中的模型别名替代实际连接配置，不静默切换模型。

正式检索配置为 FTS、向量召回与精排；运行前及每次冻结快照时检查索引完成度、集合存在性、事件映射与服务健康，覆盖主任务和门禁分支。未触发检索或未加载 Skill 是系统行为，仍保留任务成绩；向量/精排不可用属于配置健康问题，必须标记对应实验的协议符合性，不能冒称完整混合检索结果。索引构建费用与在线查询 Embedding、精排费用分别记录，冻结集合复用不会消除查询本身的费用。

formal_benchmark 按阶段屏障并发：B 主任务波次最多 3 个仓库；A 每阶段最多 3 个配对、共 6 个位置同步派发；Task 提案和对应 Gate 波次各最多 3 个仓库；T4 每组最多 3 个独立克隆。正式矩阵仍为 54 个主任务位置，A/B 组次序继续按预先记录的调度种子生成，阶段顺序不变。Runner 记录波次 ID、配对 ID、派发/终止时间、任务创建顺序、结果归并顺序与各波冻结输入指纹。`execution.max_total_tokens` 的默认值为 `100000000` Token，可在批次前调整；它是 ModelClient 生成模型 Token 账本上限，覆盖被该账本记录的 Agent、Evolution 与 Gate 调用。实际执行仍须显式传入正数 `--max-total-tokens`，并在批次清单记录实际值。Embedding/Rerank 请求未接入该账本，须单独记录检索 Token 与费用；未知用量记为未知，不能计入该上限或补零。在线、历史生成、Task 学习、Meta 学习、Gate 和回归重放分别记账。共享账本按请求到达顺序原子预留；若预算耗尽影响任一波次或 A 配对，正式批次标记不完整，配对统计只用两臂都完成的配对，不能将缺臂结果称为完整对照结论。

## 11. 运行数量与计数边界

| 范围 | 主任务运行数 |
|---|---:|---:|
| A：3 项目 × T2/T3/T4 × 2 组 | 18 |
| B：3 项目 × T1/T2/T3/T4 × 3 组 | 36 |
| 合计 | 54 |

公共历史生成、候选生成、Gate 对照、Meta 下游评估、固定回归重放和 NSRR 检查另计，不纳入 54 次主任务运行。任务数为 12；单次正式运行不能估计重复间方差，54 个执行位置也不是独立题目数。

单项目工程闭环对应 A 的 6 次运行与 B 的 12 次运行，共 18 次主任务执行位置；工程验收只执行一次，不合并进正式结果。单项目配置中的 Meta Review 在该项目 T2 后触发，明确标记 `profile=chain_integration`、`formal_results=false`；正式配置仍在三个项目 T2 批次结束后触发。

### 11.1 Profile、门禁与回归矩阵

`benchmark/configs/protocol.yaml` 已提供 `profiles.chain_integration` 与 `profiles.formal_benchmark`。各阶段的实际题目 ID 须在题集制作后填入，并在运行前通过就绪检查；配置结构就绪不等于题集或 Runner 已完成。

| 配置项 | chain_integration | formal_benchmark |
|---|---|---|
| 仓库 | repo_api | repo_api、repo_cli、repo_data |
| 重复与正式结果 | 一次；formal_results=false | 一次；formal_results=true |
| seed | 42 | 42 |
| 主任务执行位置 | A 6 + B 12 = 18 | A 18 + B 36 = 54 |
| B4 Meta Review 屏障 | repo_api.T2 结束并完成其 Task 学习 | 三个仓库 T2 结束并完成全部 Task 学习 |
| Task 发布门禁 | repo_api 对应的独立 Gate 题 | Project 按仓库作用域选择；General 按预先定义的跨仓库适用范围选择 |
| Meta 发布门禁 | repo_api 对应的独立下游 Gate 题 | 使用三个项目的预定义下游检查矩阵，核对各可比项的派生 Skill 注入证据 |
| 固定回归 | repo_api 对应集合 | 三个项目的固定集合；任务 ID、作用域与比较版本在批次前固化 |
| NSRR 独立审计 | 不运行完整八候选审计；标记 not_run，指标 N/A | 运行全部八个候选及独立审计集合，按实际结果标注 |

每个 profile 显式声明仓库、Meta 屏障仓库、各阶段 Gate task IDs、固定 regression task IDs、NSRR 开关与审计 task IDs。Runner 按 `profile × stage × candidate_scope` 解析允许集合，验证题目所属仓库、时间范围和私有文件映射，禁止仅扫描目录后把全部题目交给门禁。主任务 T4 及其隐藏验收永不用于发布选择。

矩阵中的私有文件只交给可信 Gate/Grader，按评估动作选择所需内容；不能把 `private/` 整体挂载到 Agent 工作区。缺少本 profile 要求的 Gate 或回归题时明确记录未验证，不扩大到其他 profile 兜底。链路检查中的局部门禁/回归记录不代替正式 NSRR 或跨项目回归结果。

## 12. 指标与报告

| 指标 | 固定口径 |
|---|---|
| Solve Rate | 隐藏修复及回归测试全部通过数 / 有效判分任务数；同时展示成功数 / 计划数与覆盖率 |
| Tool Calls per Solved Task | 成功任务在线工具调用量 / 成功数；无成功时 N/A |
| Tokens per Solved Task | 成功任务在线 Planner/Coder Token / 成功数；学习与评估成本单列，并报告包含学习的总成本 |
| Skill Transfer Success | T2 与 T4 分别报告成功数 / 有效判分数；该任务不得参与所测 Skill 的生成或选择 |
| Regression Rate | 固定回归题上旧版通过而新版失败数 / 旧版通过数；同题、同环境与预算重放 |
| NSRR | 独立评估标注无增益或有回归的候选中，被 Gate 拦截的数量 / 该类候选总数 |

额外保存所有失败任务成本、双方共同成功题上的配对成本、检索/注入诊断与基础设施错误。分别报告 ModelClient 生成模型账本用量和 Embedding/Rerank 检索用量；后者不受 `max_total_tokens` 账本上限约束。未知 Token 用量记为未知，不补零；优先保留服务原始用量字段，不混淆总量、缓存量与计费用量。含学习成本的主报告同时给出批次总开销 / 主任务成功数，不把共享学习成本任意归给某道题。

NSRR 固定准备八个候选检查位置：两个重复候选、两个过期候选、两个潜在回归候选、两个潜在有益候选。类型描述不是有效性标签，最终标签由独立评估产生，证据不足记 `unknown`。报告 K/N、有益候选接受/误拒计数和未知数量；分母为零时 N/A。全部候选拒绝不代表门禁质量优良。

报告按重复、项目、阶段和实验组列出原始计数及配对差异。三道 T4 只能支持有限任务范围内的观察，不预设正向效果，不宣称广泛统计显著性。展示案例从实际运行中选取并链接原始证据。

## 13. 单项目四阶段闭环的具体内容

首先实现 `repo_api`。它围绕输入校验与错误响应展开，四个阶段分别设计基础缺陷、不同端点迁移、校验/响应接口重构、组合边界留出任务。具体接口与输入数据在题目 manifest 和任务文件中定义；隐藏测试与参考补丁独立存放。

闭环需要串起五个职责：

1. Dataset：制作阶段代码、任务说明、公开检查、私有测试、参考修复及仅含当期历史的 Git 包。
2. Agent Adapter：通过 EvoCode 公开 HTTP 接口运行同一个 Agent，导出事件、模型调用和终态；正式适配代码位于 `benchmark/runner/`。
3. Experiment Runner：实现 A 的公共历史和配对运行、B 的阶段学习、Meta Review、状态冻结、预算和断点恢复。
4. Private Grader：保存完整修改产物，在干净环境重放并独立判分，保存完整日志。
5. Reporter：从结果文件生成逐题 JSON、聚合 CSV、Markdown 报告以及证据路径索引，不从 Agent 文本提取“成绩”。

可以复用现有 `scripts/blackbox_runtime.py` 的实例与遥测设计、`SandboxEvaluator` 的发布评估能力、状态快照及 Token 账本。正式 Runner 必须修正现有预验证的两处设置：Raw-RAG ON/OFF 不再各自生成不同历史；B2/B3/B4 不再关闭 Raw-RAG。Agent 通用能力如需改进，改动仍属于 Agent 代码仓库；Benchmark 专属逻辑全部放在一级 `benchmark/`。

实现对接按以下五项验收：第 9.1 节的冻结集合实际透传与内容一致性；第 7.1 节的增量索引及全检索链路边界；第 7.2、8 节的显式轨迹、异步评估等待与 Meta 反馈范围；第 4.1 节的 T3 实际适用性检查；第 11.1 节的 profile 门禁、回归与审计矩阵。接口改动必须保持普通 Agent 调用兼容，Benchmark 专属编排放在 `benchmark/runner/`。

单项目离线检查不调用模型，只验证题目、包、补丁与判分链路；真实模型工程检查显式启动，逐项记录实际用量。离线结果不能写成 Agent 能力成绩。

## 14. 状态机、恢复与产物

任务尝试的持久化阶段固定为：`planned → prepared → agent_running → artifact_saved → grading → recorded`。异常写入实际终止原因；学习过程另外记录候选、评估、发布或拒绝状态。组状态只有在阶段学习与索引任务结束后才能生成下一阶段快照。

每个阶段索引、每仓库 Task 学习、Meta Review、评估与发布都记录稳定动作标识，关联 batch/profile/组/repeat/stage/repository、输入指纹及实际 run_id。当前手动 `trigger` 不自动去重，Runner 恢复时须先核对动作账本与服务记录，复用已有作业并等待其真实状态；响应丢失或状态不明时先对账，不能直接再次触发。若现有接口无法可靠消除重复提交歧义，应补充服务端幂等键支持，未确认前不宣称“恰好执行一次”。

中断后，已保存修改产物可以重新判分；不能重新运行 Agent 后覆盖同一尝试。确需重新执行时建立新的 attempt_id，保留旧结果和原因。基础设施故障的替代尝试必须留存关联与全部成本；Agent 正常失败、超时或预算耗尽不作为基础设施重试理由。清理采用 finally，停止子进程组、回收临时容器与索引集合，保留必要诊断产物。

每次执行至少保存：协议标识、配置和代码指纹、正式/工程 profile、run/attempt/task/repeat 标识、代码与历史快照哈希、历史读取上界、实际开关、模型和参数、加载 Skill/Meta 版本、检索与上下文证据、角色用量、完整修改产物、独立 Grader 结果、学习与门禁结果、终止原因及产物路径。运行文件不保存 API Key。

实现对齐后的附加证据包括：冻结集合描述及 SQLite/向量映射核对、增量索引状态、允许历史任务/事件范围、自身任务与展开边界过滤记录、实际 trace_task_ids 与 Meta 摘要 evolution_run_ids、阶段动作账本、所选 Gate/回归/审计任务矩阵及 T3 各检查项结果。恢复过程保留原动作与新增尝试的关联，不覆盖原始证据。

各组结果 JSON、事件、补丁与判分日志放在 `benchmark/results/<batch_id>/`；汇总报告放在 `benchmark/reports/<batch_id>/`。结果中的路径以 Benchmark 根目录为基准解析，不能依赖开发者启动命令时所在目录。
